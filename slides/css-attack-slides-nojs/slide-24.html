Your “safe” CSS mutated into malicious when it was read back.

Fastmail parsed the stylesheet through the CSSOM. But the browser decodes escapes on read-back — so harmless input turned into a selector that escaped its sandbox.

Reported by PortSwigger · two $1,000 bounties · fixed

before read-back — looks fine

@keyframes foo\7d\2a { }

browser decodes \7d\2a

after read-back — now hostile

@keyframes foo }* { … }

This one genuinely surprises people, including security folk. Even "parse it properly" fails. Fastmail used the CSSOM to read what the browser actually parsed — the right instinct — but when you read certain values back, the browser DECODES hex escapes, so \7d\2a becomes }* which breaks out of the scoping prefix Fastmail added, letting the attacker's CSS control trusted UI outside the email. This is "mutation": safe-in, malicious-out, caused by the browser's own normalisation. PortSwigger got two $1k bounties and Fastmail fixed it well. Don't over-explain the escapes; the point is the shape. ~55 seconds. Then: "fine, I'll block all external requests."
